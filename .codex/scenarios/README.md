# Сценарии результатов действий

`cases.json` содержит критерии по реальным ошибкам 5 октября. Проверка трассы:

```bash
python3 .codex/tools/check_scenarios.py --trace TRACE.json
```

Трасса содержит `schema_version: 1`, `case_id`, `provenance` (`fixture` или `observed`), `events`. События идут в порядке исполнения:

Для файлов трасса также содержит `inputs.desktop_dir` — фактический абсолютный путь рабочего стола тестового пользователя, для сохранения — `inputs.expected_content_sha256`, вычисленный из ожидаемого нового текста до действия. Имя файла берётся из критерия в `cases.json`; наблюдение не может само назначить себе правильный путь или хеш. Для PDF фиксированный тестовый файл — `resume.pdf`.

- `tool`: `name`, `arguments`, `ok` — фактический вызов и результат.
- `observation`: `kind` и поля состояния, полученные от проверяющего инструмента после действия. Это может быть реальный Windows-инспектор, проверка файла или HTTP/socket.
- `claim`: `success: true` — приложение объявило успешный результат.

Наблюдения:

| kind | Поля |
| --- | --- |
| file_saved | `path`, `content_sha256`, `changed` |
| file_opened | `path`, `opened` |
| browser_focused | `focused`, `opened_urls` (список) |
| text_replaced | `changed`, `file_deleted` |
| voice_ready | `stt_ready`, `tts_ready` |
| ipc_ready | `connected`, `port` |

Итог `pass` требует соответствующего наблюдения после действия. Отсутствие данных — `unknown`, а явное нарушение или объявленный успех без подтверждения — `fail`. Для `observed` обязательны `source` и `source_sha256`: путь относительно корня к JSON-файлу доказательства и его SHA256. Источник содержит `schema_version: 1`, `provenance: observed`, тот же `case_id`, `inputs` и события, `observer` (проверяющий инструмент) и `environment` с полем `os`. Нельзя указать файл фикстуры как доказательство реального запуска. Даже `pass` на фикстуре не является аппаратной приёмкой.

`observed-2026-10-05.json` — краткая ручная реконструкция событий из логов; она имеет происхождение `fixture`, потому что у журнала нет полных аргументов инструментов и наблюдений состояния Windows. Известные нарушения остаются видимыми. Сам журнал анализируется отдельным скриптом без изменения исходного архива.

Запуск проверок самого механизма: `python3 -m unittest discover -s .codex/tests -v`. Эти тесты проверяют отказ принять старый файл за новый, ложное сохранение, удаление вместо изменения текста, устаревшие наблюдения и отсутствие доказательства. Исправление приложения оформляется отдельной задачей с трассой `observed`.
